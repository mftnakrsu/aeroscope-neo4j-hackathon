AeroScope

An aerospace requirements traceability agent on Neo4j Aura.

Ask in plain English what breaks if you change a single requirement - the agent walks the graph, names each trace hop, and cites the standards at risk.

Try the agent View on GitHub

What it does

AeroScope is a requirements-engineering agent for the systems engineer who just got a change request at 4pm and has to answer "what else does this break?" before standup tomorrow. Instead of paging through a thousand requirements in IBM DOORS, the engineer asks in plain English and gets a traced, cited answer: upstream stakeholder needs, downstream test procedures, the standards clauses at risk, and the implicit dependencies nobody wrote down.

It is not RAG over PDFs. It is an agent that walks a graph of engineering intent, names its trace path, and explains its reasoning, one hop at a time.

Impact analysis Cypher Template

If we raise the 28V DC bus undervoltage threshold on Stratos-7 from 22 V to 24 V, which requirements are affected, which tests must rerun, and what standards could we fall out of compliance with?

Answer. Pivots on the 28V threshold clause, fans out through DERIVES_FROM, SATISFIES, REFINES, and LLM-discovered SEMANTICALLY_DEPENDS_ON / CONSTRAINS edges up to three hops, then joins on VERIFIED_BY test procedures and REFERENCES_STANDARD clauses. Returns affected requirements with the exact chain of edge types, a deduplicated rerun-test list, and the standards (DO-178C, ARP4754A, MIL-STD-1553B) whose compliance evidence the change invalidates.

MATCH (anchor:Requirement)
WHERE anchor.full_text =~ '(?i).*28\s*V.*undervoltage.*'
  AND (anchor)-[:ALLOCATED_TO]->(:Platform {name: 'Stratos-7'})
CALL {
  WITH anchor
  MATCH path = (anchor)<-[:DERIVES_FROM|SATISFIES|REFINES
    |SEMANTICALLY_DEPENDS_ON|CONSTRAINS*1..3]-(dependent:Requirement)
  RETURN dependent, [r IN relationships(path) | type(r)] AS chain
}
OPTIONAL MATCH (dependent)-[:VERIFIED_BY]->(t:TestProcedure)
OPTIONAL MATCH (dependent)-[:REFERENCES_STANDARD]->(s:Standard)
RETURN dependent.id, dependent.heading, chain,
       collect(DISTINCT t.name) AS tests_to_rerun,
       collect(DISTINCT s.name) AS standards_at_risk
ORDER BY size(chain) ASC;
Compliance Cypher Template

List every requirement that references DO-178C at Design Assurance Level B, grouped by module, and tell me which ones do not yet have a linked verification procedure.

Answer. Module-grouped DAL-B scope list with each row marked as either a verification procedure name or an explicit GAP. A summary header reports total in scope, total covered, and coverage percentage. Gaps float to the top of each module so a DER's eye lands on them first - the exact evidence pack asked for at a Stage-of-Involvement audit.

MATCH (r:Requirement)-[ref:REFERENCES_STANDARD]->(s:Standard {name: 'DO-178C'})
WHERE ref.dal = 'B' OR r.dal = 'B'
OPTIONAL MATCH (r)-[:VERIFIED_BY]->(t:TestProcedure)
RETURN r.module,
       r.id,
       r.heading,
       CASE WHEN t IS NULL THEN 'GAP' ELSE t.name END AS verification_status
ORDER BY r.module, verification_status DESC, r.id;
Semantic search Similarity Search

Find me other requirements across the fleet that describe the same behaviour as REQ-FCC-118 (pitch-rate limiter during recovery), even if they are written in different words or live in different modules.

Answer. Top-K cosine similarity on the 1536-dim embedding index, enriched with graph context: each candidate is annotated with platform allocation and a boolean already_linked flag showing whether the pair is connected by any relationship. An action column suggests merge, add an explicit REFINES edge, or leave as a legitimate parallel implementation.

MATCH (anchor:Requirement {id: 'REQ-FCC-118'})
CALL db.index.vector.queryNodes('requirement_embeddings', 15, anchor.embedding)
YIELD node AS candidate, score
WHERE candidate.id <> anchor.id

OPTIONAL MATCH (candidate)-[:ALLOCATED_TO]->(p:Platform)
OPTIONAL MATCH (candidate)-[:DERIVES_FROM|SATISFIES
  |SEMANTICALLY_DEPENDS_ON]-(anchor)
RETURN candidate.id, candidate.module, candidate.heading, score,
       collect(DISTINCT p.name) AS platforms,
       exists((candidate)--(anchor)) AS already_linked;

Why a graph

  • Relationships are the data. Take away SATISFIES, DERIVES_FROM, VERIFIES, REFERENCES_STANDARD, ALLOCATED_TO and you are left with a thousand disconnected sentences.
  • Explain why, not just what. The trace path itself, serialised into English, is the explanation - the engineer defends the answer without trusting the LLM.
  • LLM-discovered implicit edges. SEMANTICALLY_DEPENDS_ON, COMPLEMENTS, CONSTRAINS, POTENTIALLY_CONFLICTS surface dependencies that are real in the system but were never written into a formal trace link - the gap plain-text search cannot cross.

How to build your own

  1. Generate the corpus. Produce ~1000 synthetic requirements in the IBM DOORS 9.7 MD export format - the same shape the pipeline accepts for real industry data.
  2. Load into Neo4j Aura. Parse to JSONL, build nodes and trace edges, extract entities (Standards, Interfaces, Components, Platforms), and auto-link cross-references.
  3. Enrich. Compute 1536-dim embeddings, generate one-line summaries, and run an offline LLM pass that discovers implicit SEMANTICALLY_DEPENDS_ON / COMPLEMENTS / CONSTRAINS / POTENTIALLY_CONFLICTS edges.
  4. Wire up the agent. In the Aura Agent console, bind three tools - Cypher Template, Text2Cypher, Similarity Search - to the populated database, expose it via External Access or MCP, and ask away.
